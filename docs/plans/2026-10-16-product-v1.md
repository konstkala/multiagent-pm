# Product plan v1: AI-assisted project management

Supersedes the scope of [ticket triage v1](2026-10-16-ticket-triage-v1.md). Everything built there is reused.
The [phase 4 triage plan](2026-10-16-phase4-triage-workflow.md) becomes milestone 4, extended below.

## The product
Managers run projects with their teams. Agents do the tedious parts: classifying and sizing tickets, turning CVs into skill profiles, and recommending who should take a ticket. People make every consequential decision.

## Domain
- **Workspace** (a company). Users belong to workspaces. Data never crosses workspaces.
- **Project** with a short key (`PM`), like Jira. Ticket numbers are per project: `PM-42`.
- **Project member**: user + role (`manager` or `employee`).
- **Employee profile**: skills (with level), experience, summary. Created from a CV by an agent and reviewed by a manager. The CV file is deleted after extraction unless the manager keeps it, and on request.
- **Ticket**: title, description, category (bug, implementation, analysis, ...), labels (area: database, frontend, backend, ...), story points, due date, reporter, assignee, status, parent ticket (sub-tasks), links (blocks / relates to / duplicate of), comments, attachments.
- **Status flow**: To do → In progress → In review → Done; Cancelled. Employees move to In review (with proof); only managers move to Done or Cancelled. "Return to manager" unassigns, with a required reason.

## Agents
| Agent | Trigger | Model | Est. cost | Human control |
|---|---|---|---|---|
| Triage: category, labels, points, sub-task hints; reads images and linked tickets | Ticket created or copied | Haiku 5.5 (vision) | ~$0.002 / ticket | Low confidence → one clarifying question to the manager; points need approval |
| CV → profile | CV uploaded | Haiku 5.5 (PDF input) | ~$0.002 / CV | Manager reviews before saving |
| Assignment | Manager clicks "Suggest assignee" | Code scoring + Haiku for reasons | ~$0.001 / click | Manager picks from the top 3 |

Assignment scoring (code, testable): skill match (embeddings of ticket vs profile), open story points, overdue tickets, similar tickets done before. The LLM only writes the explanation.

## KPIs (time-filtered, per project)
Throughput (done per period), cycle time (in progress → done), lead time, open and overdue by status and age, workload (open points per person), estimate accuracy (agent points vs actual). Team-level for everyone; individual figures visible only to managers and to the person.

## Milestone 1a design
- **Sessions, not JWTs.** Random opaque token in an `httpOnly`, `Secure`, `SameSite=Lax` cookie; only its SHA-256 hash is stored, so a database leak can't be replayed. Sessions are revocable (sign out everywhere). 14-day expiry.
- **CSRF**: `SameSite=Lax` cookie plus a required custom header on state-changing requests.
- **Passwords**: argon2id; minimum 10 characters; rehash on login if parameters change.
- **Email tokens** (verify, reset): random, single-use, stored hashed, short expiry (verify 24 h, reset 30 min). A password reset signs out every other session.
- **No account enumeration**: sign-up, sign-in and reset return the same messages whether an email exists or not.
- **Rate limits** on sign-in and reset (per email and per IP).
- **Logs**: `audit.auth.*` events with user id, never emails, passwords or tokens.
- **Email**: SMTP; locally Mailpit (a fake inbox at http://localhost:8025).
